## 2. Incomplete or placeholder features

### GAP-01 — No user or access administration interface — **P0**
- **Evidence:** `src/app/settings/page.tsx` is a `ModulePlaceholder` (line 2,
  line 13). `grep ModulePlaceholder src` returns only that page and the
  component itself. There is no `src/lib/users*`, no user service, no user
  server action, and no `/settings/users` route.
- **Impact:** an administrator cannot create an account, disable a leaver or
  change anyone's roles. The only way to create an account is `npm run db:seed`.
- **Affected files:** `src/app/settings/page.tsx`, `src/lib/transport/actions.ts`,
  `src/lib/rbac.ts`, new `src/lib/users/**`.
- **Acceptance criteria:** list + search users; create with a forced
  initial-password workflow; disable/re-enable; assign/revoke the four
  provisional roles; assign/revoke operator scope; every mutation
  permission-checked server-side, audited, and with validation errors shown in
  the UI.

### GAP-02 — Accounts cannot be disabled at all — **P0**
- **Evidence:** `prisma/schema.prisma` lines 29–47 — the `User` model has
  `id, name, email, emailVerified, image, createdAt, updatedAt` and relations.
  There is no status/disabled field. `getCurrentUser()`
  (`src/lib/authorization.ts`) never checks one.
- **Impact:** disabling a user is impossible, so a departing employee keeps
  access until their session expires.
- **Acceptance criteria:** additive migration adds a disable marker; a disabled
  user's sessions are rejected on the very next request.

### GAP-03 — No session-revocation service — **P0**
- **Evidence:** the only sign-out path is the browser call
  `authClient.signOut()` in `src/components/shell/UserTopBar.tsx:64`. `grep` for
  `session.deleteMany|revokeSession` finds no server-side helper.
- **Impact:** an access change cannot take effect immediately for an
  already-signed-in user.
- **Acceptance criteria:** a server helper deletes a user's session rows, called
  automatically on disable and on privilege-reducing role changes.

### GAP-15 — No account-creation workflow — **P0** (part of GAP-01)
- **Evidence:** accounts exist only via `prisma/seed.ts`
  (`ensureDevelopmentAdmin`). Public signup is disabled
  (`disableSignUp: true` in `src/lib/auth.ts`).
- **Acceptance criteria:** an administrator can create an account and is shown
  the initial password exactly once, never stored or logged in plaintext.

## 3. Security and privacy risks

### GAP-04 — No login rate limiting or abuse monitoring — **P0**
- **Evidence:** case-insensitive searches across `src`, `scripts`, `tests`,
  `prisma` for `rate.limit`, `throttle`, `429` and `lockout` return **0**
  matches. `src/lib/auth.ts` mounts Better Auth with no rate-limit option, and
  `src/app/api/auth/[...all]/route.ts` is a bare `toNextJsHandler(auth)`.
- **Impact:** unlimited password guessing against a known account (the seed
  email is discoverable), and no signal that an attack is underway.
- **Acceptance criteria:** sliding-window limiting that (a) works behind a
  trusted proxy without trusting client-supplied headers, (b) **cannot** be used
  to lock a victim out from a third-party IP, (c) emits an audit event when it
  triggers, (d) returns HTTP 429 with `Retry-After`.

### GAP-05 — Audit IP handling is spoofable and weakly hashed — **P1**
- **Evidence:**
  - `src/lib/audit.ts:26-29` — `hashIp` is an **unkeyed** SHA-256 truncated to
    32 hex chars. The IPv4 space is only 2³², so the stored value can be
    brute-forced back to an address in minutes; the "non-reversible" comment
    overstates the protection.
  - `src/lib/auth-audit.ts` `extractClientMeta()` reads
    `x-forwarded-for`'s first element unconditionally, with no notion of a
    trusted proxy. Any client can set that header and choose what gets recorded.
- **Impact:** audit IP evidence is both forgeable and reversible.
- **Acceptance criteria:** proxy trust is explicit and configurable (default:
  trust nothing); the stored hash is keyed (HMAC) so it is not reversible;
  behaviour is unit tested for both trust modes.

### GAP-06 — Audit write failures are silently swallowed — **P1**
- **Evidence:** `src/lib/audit.ts:36-57` — `recordAuditEvent` returns `void`,
  catches every error and only calls `console.error`. A caller cannot tell
  whether the event was persisted, and nothing aggregates or alerts on failures.
- **Impact:** an attacker who can make the audit insert fail (or a DB outage)
  creates a silent audit gap with no monitoring signal.
- **Acceptance criteria:** the function reports persistence success/failure, a
  failure counter is exposed for monitoring, and the trade-off (in-process only)
  is documented rather than overclaimed.

### GAP-07 — No encryption-key rotation, recovery or failure handling — **P1**
- **Evidence:** `src/lib/crypto/field-crypto.ts` reads a single
  `FIELD_ENCRYPTION_KEY` (`getFieldEncryptionKey`) and encrypts as
  `v1:<iv>:<authTag>:<ciphertext>` — the payload carries **no key identifier**.
  There is no re-encryption routine anywhere.
- **Impact:** rotating the key makes every existing passenger record
  permanently unreadable (`decryptField` throws). There is no way to know which
  key a row used, and no migration path.
- **Acceptance criteria:** payloads identify their key; multiple keys can be
  configured; legacy payloads still decrypt; a rotation tool re-encrypts
  existing rows in batches with a dry-run default and a verification mode; unit
  and live tests cover the transition.

### GAP-08 — Runtime database user holds DDL privileges — **P1**
- **Evidence:** `db/setup-db.sql:34-35` grants `ALL PRIVILEGES ON
  bpta_transport_dev.*` to `bpta_app`, which the application uses at runtime.
- **Impact:** an SQL-injection or compromised runtime credential could `DROP` or
  `ALTER` tables. Least privilege is not applied.
- **Acceptance criteria:** a separate migration user holds DDL; the runtime user
  holds only `SELECT/INSERT/UPDATE/DELETE`; the change is documented and applied
  by an operator with `root` (the application account cannot grant privileges
  and the audit must not attempt it).

### GAP-13 — Audit trail is not tamper-resistant — **P2 (confirmed, not a regression)**
- **Evidence:** `docs/PHASE_8_SECURITY_REVIEW.md` documents this honestly, and
  `src/app/audit/page.tsx` warns the user in the UI. No append-only DB role,
  checksum chain or off-host shipping exists in source.
- **Action:** keep the honest wording. Do not claim immutability. Re-assess only
  if real integrity engineering is added.

### GAP-16 — Demo-only admin endpoints still exposed — **P3**
- **Evidence:** `src/app/api/admin/ping/route.ts` and
  `src/app/api/admin/protected/route.ts` are demonstration endpoints used by
  tests.
- **Action:** keep (they are permission-gated and asserted by the live smoke
  test), but document that they are demonstrations, not product features.

## 4. Database and migration risks

| Risk | Evidence | Mitigation planned |
|---|---|---|
| `prisma migrate dev` cannot run with the least-privilege account (needs a shadow DB; `error 1142`) | Reproduced earlier in this project; documented in `docs/PHASE_3_TRANSPORT_ADMIN.md` §6 | Continue using `migrate diff` → review SQL → `migrate deploy`; documented in the installation guide |
| New work needs schema changes (disable flag, rate-limit ledger) | GAP-02, GAP-04 | One additive migration: add a nullable column and one new table; review the SQL before applying |
| Migration SQL is generated by diff, so a mistake would not be caught by a shadow DB | Process risk | Read every generated statement; assert it contains no `DROP`, `TRUNCATE` or `DELETE` before applying |
| No automated migration checksum verification in CI | No CI exists | Documented; not addressed in this stage |

## 6. Internationalization and accessibility gaps

### GAP-09 — No internationalization foundation — **P1**
- **Evidence:** `src/app/layout.tsx:42` hardcodes `<html lang="en">` with no
  `dir` attribute. Searches for `i18n`, `locale`, `rtl`, `Intl` return 0 matches
  in `src`. No dictionaries, no language selector, no locale cookie.
- **Impact:** the project brief requires English, Urdu, Pashto and Balochi, with
  RTL; a settlement that reads right-to-left is not served at all.
- **Acceptance criteria:** a locale foundation with 4 languages, correct
  direction, a selector that persists the choice, applied to the shell and
  navigation; no legal or official wording is machine-translated as though
  approved.

### GAP-17 — Accessibility never independently audited — **P2**
- **Evidence:** `docs/PHASE_8_SECURITY_REVIEW.md` §8 states plainly that no
  axe/Lighthouse audit, screen-reader test or keyboard-only walkthrough was
  performed.
- **Action:** add automated accessibility assertions to the browser E2E suite
  (semantic landmarks, labels, focusability) and report what remains manual.
